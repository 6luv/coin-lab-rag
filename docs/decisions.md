# 기술 결정 기록

## D1. 항목 출처로 CoinGecko 공개 API 사용 (2026-10-22)
- 근거: 키 없이도 시가총액 순 목록·상세(카테고리·출시일·설명·백서 링크)를 JSON으로 제공, 150건 수집 실측 확인.
- 제약: 키 없는 호출은 공용 IP 단위 한도 → Demo 키 권장. 약관상 저장 비권장·24시간 내 갱신·"Powered by CoinGecko" 표기.

## D2. 코인 ↔ 위키 문서 연결은 위키데이터 P5777 우선 (2026-10-22)
- 근거: 이름 검색은 동음이의(예: Stellar, Sky, Rain) 오매칭 위험. P5777(CoinMarketCap ID) slug 가 CoinGecko id 와 대부분 일치해 정확한 연결 가능.
- 순서: P5777=coingecko_id → P5777=name_slug → 라벨 검색+설명 필터. 매핑 방법을 `source_map.json`에 남겨 검증 가능하게 함.

## D3. 가격은 색인 텍스트에서 제외 (2026-10-22)
- 근거: 가격은 매일 바뀌어 임베딩이 금방 낡고, 조건 검색에도 쓰이지 않음. 메타데이터·화면 표시로만 사용하고 기준 시각을 표기.

## D4. 청크 1,000자 / 중복 200자, Top-k 6 으로 시작 (2026-10-22)
- 근거: 명세 예시값. 한국어 위키 코인 문서 평균 약 4,000자 → 문서당 4~6청크. 검증 단계에서 500/100, 1,500/300 과 비교 예정.

## D5. 화면은 web/ (HTML·CSS·JS) + 샘플 모드 (2026-10-22)
- 근거: 사용자 요청(web 폴더 참고). 서버가 없어도 코인 선택·정보·키워드 탐색을 확인할 수 있게 `web/sample/coins_sample.js` 를 둠. 샘플 모드는 화면에 명시.

## D6. 위키 문서 연결의 사람 검토 규칙 (2026-10-22)
- 규칙: 문서가 토큰의 프로토콜·플랫폼 자체를 다루면 accept, 별개의 발행사·거래소·회사 문서면 related.
- related 문서는 '항목 자체 문서'(F2004 우선 색인)로 쓰지 않고 질문 기반 수집 후보로만 쓴다. 결과는 `source_map.json`의 `candidate_review`/`link_review`.
- 근거: 제목이 정확히 일치해도 다른 대상인 사례(Rain → 바레인 거래소), 발행사 문서가 토큰 문서로 붙는 사례(KuCoin, USD1)를 실제 데이터에서 확인.

## D7. CoinGecko 파생 데이터는 git 에 올리지 않음 (2026-10-22)
- `data/raw/`, `data/coins.json`, `web/sample/coins_sample.js` 는 `.gitignore`. 각자 `collect_coins` 로 받는다.
- 근거: 약관의 저장 비권장·24시간 갱신·재배포 제한. 테스트·점검 스크립트는 파일이 없으면 안내 후 건너뛴다.

## D8. 화면 디자인은 DESIGN.md 로 관리, 3열 대시보드 (2026-10-22)
- 레퍼런스(CodePen "Crypto Live Price Chart")의 색·글꼴·위젯 형태를 따르되, 가짜 시세 애니메이션은 쓰지 않고 스냅샷 값만 표시.
- 차트: 24H·7D 는 CoinGecko markets `sparkline=true` 의 7일 시간별 가격(코인 150개를 호출 1번으로 받음), 30D 는 변동률 역산 추정치로 표시하고 화면에 추정임을 밝힘. 코인별 `market_chart` 호출은 키 없는 한도(약 1건/분)로 150개에 2시간 이상 걸려 채택하지 않음.
- 라이트 모드가 기본(사용자 요청), 화면 시각은 KST. 데이터 파일은 UTC 로 저장.

## D9. RAG 파이프라인·서버 구성 (2026-10-22)
- 프롬프트는 도메인에 묶이므로 `src/data_prep/prompts.py` 에 둔다 (NF2005). LLM 출력은 JSON 으로 받고, 파싱 실패 시 검색어는 질문 원문, 선별·추천은 "선택 없음"으로 안전하게 처리.
- 특화 기능(리스크 브리핑·팩트체크)은 같은 LangGraph 를 mode 만 바꿔 실행해 근거 표시 규칙을 공유한다.
- 질문마다 수집한 문서는 바로 coin_docs 에 색인한다. 수집은 서버 안에서 잠금으로 한 번에 하나씩.
- GMS 주소 `https://gms.ssafy.io/gmsapi/api.openai.com/v1` 은 GMS 안내(사용자 제공, `POST .../v1/responses`)로 확인. 채팅은 Responses API(`use_responses_api`), 키는 환경 변수 `GMS_KEY` 로만 읽는다. `OPENAI_BASE_URL` 로 덮어쓸 수 있다.
- 오류 응답은 사용자용 문장만, 스택트레이스는 서버 로그에만 (NF2004).
- 수집 기록(manifest)은 중간에 실패해도 항상 저장한다. 실패 복구 규칙은 D10.
- 수집 잠금은 서버 전체 하나라 동시 질문은 차례로 처리된다 (시연 규모에서 허용, 필요 시 코인별 잠금으로 변경).

## D10. 색인·수집 실패 복구 규칙 (2026-10-22, Codex 검증 반영)
- 색인은 새 청크 upsert → 새 목록에 없는 이전 청크 삭제 순서. 임베딩 호출이 실패하면 이전 색인이 남는다.
- 문서 저장(`save_doc`)과 검색어 완료 기록(`mark_keyword`)을 분리한다. 검색어는 그 검색어로 고른 문서의 본문 수집·색인이 모두 성공했을 때만 기록해, 일시 장애 뒤 같은 질문으로 다시 수집된다.
- 저장 파일은 있는데 색인에 없는 문서는 그 코인을 다음에 수집할 때 저장 파일로 재색인한다 (자체 문서·질문 문서 공통).
- 문서 파일 이름과 중복 판단은 `(coin_id, doc_id)` 기준. 제목 기준이면 언어가 다른 동명 문서가 서로 덮어쓴다.

## D11. Claude ↔ Codex 자동 호출은 CLI 오케스트레이터로 (2026-10-22)
- `scripts/agent_loop.py` 가 `claude -p`(구현)와 `codex exec`(검증)를 번갈아 새 프로세스로 실행한다. 매 호출이 새 컨텍스트라 구현과 검증이 섞이지 않는다.
- 근거: 두 CLI 모두 비대화 실행(`-p`, `exec`)과 표준입력 프롬프트를 지원하고, 서로를 직접 부르는 공식 연동은 없다. 별도 서버·큐 없이 파이썬 표준 라이브러리만 쓴다(새 의존성 없음).
- 안전: Claude 는 편집 허용 + 테스트·git 조회 명령만 허용, Codex 는 read-only 샌드박스. 검증 전후 작업 폴더 해시를 비교해 검증 담당이 파일을 바꾸면 경고한다. 커밋·푸시는 하지 않는다.
- 판정은 보고서의 `결과: PASS|FAIL` 줄로 읽고, 찾지 못하면 멈춘다. 수정 후 FAIL 이 3번이면 멈춘다 (프로젝트 지침).
- Codex 모델은 `config/agents.json` 에 지정하지 않으면 사용자 Codex 설정의 기본 모델을 쓴다.
